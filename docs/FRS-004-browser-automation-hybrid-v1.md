# FRS-004: Browser Automation — Hybrid Code-Gen + Deterministic Execution

Version: 1.0.0
Status: Implemented
Derived from: DOC-RES-2026-07-16-browser-automation-deep-research.md
Date: 2026-07-16

---

## Objective

Implement a local-first, token-efficient, enterprise-grade browser automation capability for EdgeGDE. The system lets Warren record a Salestrekker interaction once via Playwright Codegen, optimises the recorded script with an LLM pass, then executes it deterministically via a persistent Chrome profile (Steel.dev). Dynamic content (variable file counts, dropdown loops, changing values) is handled via standard JS/TS patterns injected at the recording stage, not via per-action LLM calls.

The result: zero-token runtime execution, full audit trail (trace + video + DOM snapshot), and fast recovery when UI changes (re-record the broken section in ~30 seconds).

## FRS-1: Steel.dev — Local Persistent Chrome Profile

### Objective

Provide a self-hosted, containerised Chrome instance with a persistent user profile so that authenticated sessions (Salestrekker login with 2FA) survive container restarts. No cloud dependency, no API key, no rate limits.

### Functional Requirements

**FR-1.1** — Steel.dev SHALL run as a Podman container on macOS with persistent volume `/home/chrome` mounted across restarts.

```bash
podman run -d \
  --name steel \
  --restart unless-stopped \
  -p 9222:9222 \
  -v steel-chrome-data:/home/chrome \
  steeldev/steel:latest
```

**FR-1.2** — The container SHALL expose Chrome DevTools Protocol on `localhost:9222` with no authentication (local-only).

**FR-1.3** — The container SHALL restart automatically (Docker restart policy or launchd wrapper) so Chrome survives macOS reboots.

**FR-1.4** — The persistent profile SHALL store Salestrekker session cookies, 2FA trust flags, and extension data so that password entry is a one-time operation.

**FR-1.5** — A health-check endpoint SHALL confirm CDP is reachable before any Playwright script execution begins:

```typescript
const browser = await playwright.chromium.connectOverCDP('http://localhost:9222');
const version = await browser.version();
// version >= '131.0' required
```

### Acceptance Criteria

- [ ] `podman ps` shows `steel` container running
- [ ] `curl -s http://localhost:9222/json/version` returns valid Chrome version JSON
- [ ] Playwright `connectOverCDP('http://localhost:9222')` succeeds
- [ ] Salestrekker login persists across container restart (re-authenticate once, verified on next restart)

### OTel Observability

| Span | Attribute | Status |
|------|-----------|--------|
| `steel.health_check` | `chrome.version`, `chrome.connected` | OK / FAIL |
| `steed.container_status` | `container.running`, `container.uptime_s` | OK / RESTARTED / STOPPED |

### Verification

```bash
podman ps --filter name=steel --format '{{.Status}}'
curl -s http://localhost:9222/json/version | python3 -c "import sys,json; print(json.load(sys.stdin)['Browser'])"
```

## FRS-2: Playwright Script Execution Engine

### Objective

Execute Playwright TypeScript scripts against the Steel.dev Chrome instance with deterministic output (screenshots, traces, JSON results). Scripts are generated by Codegen recording + LLM optimisation, not by per-action agent loops.

### Functional Requirements

**FR-2.1** — Scripts SHALL be standard Playwright TypeScript files executed via `npx playwright test` targeting `connectOverCDP`.

**FR-2.2** — The execution engine SHALL inject environment variables (`STEEL_URL`, dynamic values) at runtime.

**FR-2.3** — Every execution SHALL produce:
- Playwright trace (`.zip`) — full replay log of every action
- DOM snapshot — final page state as HTML
- Screenshot — full-page screenshot at completion
- JSON result — structured output (extracted data, pass/fail, error details)

**FR-2.4** — The engine SHALL support dynamic content patterns via standard JS/TS:

| Pattern | How | Example |
|---------|-----|---------|
| List iteration | `for` loop + `.count()` + `.nth(i)` | Loop through dropdown items |
| Dynamic file count | `page.locator('.row').count()` → iterate | Download N files |
| Changing values | `env` vars or page extraction | 2FA code, loan amounts |
| Wait conditions | `waitForSelector`, `waitForResponse`, `waitForEvent(download)` | Spinner, API response |

**FR-2.5** — On script failure, the engine SHALL capture the trace and screenshot at the point of failure (not just on completion).

### Acceptance Criteria

- [ ] `npx playwright test --connect localhost:9222` executes against Steel.dev
- [ ] Trace file is produced and replayable in Playwright Trace Viewer
- [ ] Screenshot captures the final page state
- [ ] Dynamic loop over N elements executes correctly with N varying between runs
- [ ] Environment variable injection works (`process.env.ST_2FA_CODE`)

### OTel Observability

| Span | Attribute | Status |
|------|-----------|--------|
| `playwright.script.execute` | `script.path`, `script.duration_ms`, `result.status` | PASS / FAIL / TIMEOUT |
| `playwright.script.trace` | `trace.path`, `screenshot.path`, `dom.path` | CAPTURED / MISSING |

### Verification

```bash
npx playwright test login-salestrekker.spec.ts --reporter=json 2>&1 | python3 -c "import sys,json; r=json.load(sys.stdin); print(r['suites'][0]['status'])"
```

## FRS-3: Codegen Recording + LLM Optimisation Workflow

### Objective

Replace per-action token-burning agent loops with a two-phase workflow: (1) human records the interaction once via Playwright Codegen, (2) LLM optimises selectors to use stable attributes. The output is a deterministic, zero-token script that runs forever (or until the UI changes).

### Functional Requirements

**FR-3.1** — The workflow SHALL support two recording modes:

| Mode | Command | Use Case |
|------|---------|----------|
| Local Chrome | `npx playwright codegen` | First-time setup, debug |
| Steel.dev | `npx playwright codegen --connect cdw://localhost:9222` | Authenticated sessions |

**FR-3.2** — The LLM optimisation pass SHALL take the raw Codegen output as input and produce:

```diff
- await page.locator('.MuiTableRow-root-12345').click();
+ await page.locator('role=row[name="Deal-2026-001"]').click();
```

- Prefer: `role=` selectors (ARIA), `data-testid`, `aria-label`, `text` (unique text)
- Avoid: class names, positional selectors, index-based selectors
- Maintain: all control flow (loops, conditions, variable references)

**FR-3.3** — Dynamic elements SHALL be handled by the LLM injecting JS patterns, not removed:

```typescript
// LLM SHOULD keep this pattern:
for (let i = 0; i < await page.locator('.deal-row').count(); i++) {
  await page.locator('.deal-row').nth(i).locator('button').click();
}
```

**FR-3.4** — The LLM SHALL NOT add new logic, change control flow, or remove human-inserted variable references.

**FR-3.5** — After LLM optimisation, the result SHALL be type-checked (`npx tsc --noEmit`) before being saved as the canonical script.

### Acceptance Criteria

- [ ] Raw Codegen output can be saved to a `.ts` file
- [ ] LLM optimisation produces a syntactically valid TypeScript file
- [ ] TypeScript compiles without errors after optimisation
- [ ] Optimised script runs against Steel.dev and produces same result as raw
- [ ] Loops and variable references survive the optimisation pass

### OTel Observability

| Span | Attribute | Status |
|------|-----------|--------|
| `codegen.optimise` | `input.selectors.count`, `output.role.selectors.pct`, `tsc.passed` | OK / TSC_FAIL / EMPTY_OUTPUT |

### Verification

```bash
# Record → Optimise → Execute
npx playwright codegen --output /tmp/raw_script.ts --target playwright-test --connect cdw://localhost:9222
# (manual: record interaction, close browser)
llm_optimise /tmp/raw_script.ts > /tmp/optimised_script.ts
npx tsc --noEmit --strict /tmp/optimised_script.ts
npx playwright test /tmp/optimised_script.ts --connect localhost:9222
```

## FRS-4: EdgeGDE Integration — Mission Manifest + Aegis Gate

### Objective

Wire browser automation into the EdgeGDE SDLC so that Hermes can schedule or trigger Playwright scripts as Droid-executable tasks, with Aegis validation and full audit trail.

### Functional Requirements

**FR-4.1** — A new operation family `browser_automation` SHALL be registered in the Mission Manifest schema with allowed operations:

| Operation | Args | Droid Executable |
|-----------|------|-----------------|
| `execute_script` | `script_path`, `env_vars`, `timeout_seconds` | ✅ Yes |
| `record_script` | `target_url`, `profile_id` | ❌ No (human via Codegen) |
| `verify_result` | `expected_selector`, `expected_text` | ✅ Yes |

**FR-4.2** — Execution SHALL produce a structured report:

```json
{
  "mission_id": "browser-auto-001",
  "script": "scripts/salestrekker-download-deals.ts",
  "status": "passed",
  "evidence": {
    "trace": ".hermes/logs/browser/2026-07-16/trace.zip",
    "screenshot": ".hermes/logs/browser/2026-07-16/final.png",
    "dom": ".hermes/logs/browser/2026-07-16/dom.html",
    "result": ".hermes/logs/browser/2026-07-16/result.json"
  },
  "duration_ms": 3420,
  "compensation": "manual"
}
```

**FR-4.3** — Aegis SHALL validate:
- Script exists in the registered scripts directory
- Script is TypeScript (not arbitrary shell)
- All referenced env vars are declared in the manifest
- No network calls to unexpected hosts

**FR-4.4** — Scripts SHALL be stored under `.hermes/browser-scripts/` with the convention:

```
.hermes/browser-scripts/
├── salestrekker/
│   ├── login.ts            # One-time, recorded
│   ├── download-deals.ts   # Per-task, recorded + optimised
│   └── fixtures/
│       └── selectors.ts    # Shared data-testid constants
└── broker-tools/
    └── ...
```

### Acceptance Criteria

- [ ] Mission Manifest accepts `browser_automation` operation type
- [ ] Aegis validates script existence before execution
- [ ] Execution report is structured JSON saved to `.hermes/logs/browser/`
- [ ] Failed execution produces trace + screenshot at failure point
- [ ] Hermes can trigger via cron: `hermes cron create "download deals every Monday"`

### OTel Observability

|------|-----------|--------|
| `aegis.validate.script` | `script.path`, `script.hash`, `validation.passed` | PASS / FAIL |
| `droid.browser.execute` | `mission.id`, `script.name`, `result.status` | PASS / FAIL / TIMEOUT |

## FRS-5: Recovery Protocol — UI Change Handling

### Objective

Define the process for when a UI change breaks a recorded script. The enterprise pattern is fast recovery (re-record the broken section), not unbreakable scripts.

### Functional Requirements

**FR-5.1** — When a script execution fails:
1. Capture the failure trace + screenshot at the point of failure
2. Log the failure to `.hermes/logs/browser/failures/` with the trace evidence
3. The human re-records the broken interaction via Codegen (targeting Steel.dev for auth):
   ```bash
   npx playwright codegen --connect cdw://localhost:9222
   ```
4. The LLM optimises the new recording (same prompt as FR-3.2)
5. The updated script replaces the old one
6. Aegis logs the selector change as a version bump

**FR-5.2** — A script SHALL be considered "stale" and flagged for re-recording if it has failed 3 consecutive times with the same error pattern (selector not found, element timeout).

**FR-5.3** — The recovery time target from detection to re-recording SHALL be <5 minutes (30 seconds Codegen recording + pipeline time).

### Acceptance Criteria

- [ ] Failure evidence (trace + screenshot) is preserved
- [ ] Re-recording via Codegen with Steel.dev works without re-authentication
- [ ] LLM optimisation of the new recording is a single prompt (not multi-turn)
- [ ] Script version is tracked (human-readable revision field)

### OTel Observability

| Span | Attribute | Status |
|------|-----------|--------|
| `browser.script.failure` | `script.path`, `error.type`, `error.selector`, `recovery.started` | FAILURE_RECORDED / RECOVERY_INITIATED |
| `browser.script.recovery` | `script.path`, `re-record.duration_s`, `selectors.changed` | RECOVERED / ESCALATED |

### Verification

```bash
# Simulate failure
# → Observe trace at failures/
# → Re-record
# → Verify optimised script against same target
```

## Boundaries

### Always do
- Connect to Steel.dev via `connectOverCDP`, never start a new browser
- Capture trace + screenshot on every execution (pass or fail)
- Use `<role=>` selectors in optimised scripts (never class-name selectors)
- Store scripts under `.hermes/browser-scripts/` with `.ts` extension
- Log all execution results to `.hermes/logs/browser/`

### Ask first
- Installing new browser dependencies (`npx playwright install chromium`)
- Changing the Steel.dev container configuration (ports, volumes)
- Storing credentials in script files (should be env vars only)
- Converting an existing Hermes computer-use task to a Playwright script

### Never do
- Run per-action LLM loops during execution (defeats token efficiency)
- Store API keys or passwords in script files (env vars only)
- Submit or finalise loan applications (draft-only per broker-skill rule)
- Use cloud browser providers (Browserbase, Hyperbrowser) for local tasks
- Execute unrecorded LLM-generated scripts without human review

## Resolved Decisions

| Question | Decision | Rationale |
|----------|----------|-----------|
| Mastra vs EdgeGDE SDLC | ✅ Skip Mastra — use existing EdgeGDE workflow engine | EdgeGDE already has deterministic workflow (Mission Manifest → Aegis → Droid). Adding Mastra duplicates that layer. |
| Codegen vs LLM-write scripts | ✅ Codegen record → LLM optimise | Human-recorded interactions are more reliable than LLM-written from empty context. LLM only refines selectors. |
| Steel.dev vs Browserbase | ✅ Steel.dev (self-hosted) | Local-first, no cloud tokens, persistent profile, free. Browserbase adds cost and cloud dependency. |
| TypeScript vs Python | ✅ TypeScript (Playwright) | Matches EdgeGDE stack (TS-native), no runtime bridge needed. |
| Per-action LLM vs code-gen | ✅ Code-gen (1-2 LLM calls per task) | Source: DOC-RES-2026-07-16 benchmark data. Code-gen is 50-100x more token-efficient than per-action loops. |
| Dynamic content handling | ✅ Standard JS/TS patterns (for loops, page extraction) | No LLM needed for iteration or value reading. One-time edit to recorded script. |
| Script storage | ✅ `.hermes/browser-scripts/` | Follows existing `.hermes/` convention for agent-managed artifacts. |

## Open Questions

1. **Steel.dev on Apple Silicon** — Steel.dev publishes amd64 images. Podman on Apple Silicon runs via Rosetta 2. Does Chrome performance degrade measurably? Alternative: use `playwright/chromium` Docker image as a free drop-in (requires manual profile management).
2. **launchd wrapper** — Should Steel.dev be managed via a macOS launchd plist for auto-start on boot, or is `--restart unless-stopped` via Podman sufficient?
3. **Global hotkey trigger** — Do we want a keyboard shortcut that opens a Codegen recording session against Steel.dev? This would speed the re-recording workflow.
4. **Initial recording session** — Do you want to record the first Salestrekker workflow together, or will you record it independently and hand off the raw output for optimisation?
